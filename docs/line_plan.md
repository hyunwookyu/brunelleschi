## 1. 제품 정의 (개정)

**투시도와 입체를 동시에 보면서 실시간으로 입체를 생성한다.**

두 표상이 동등하다. 어느 쪽을 조작해도 다른 쪽이 즉시 따라온다.
3D는 부가 기능이 아니다 — 입체를 만드는 것이 목적이고, 투시도는 그 입력이자
동시에 출력이다.

**공간과 투시를 이해하는 사용자를 전제한다.**
소실점 가이드를 맞추는 것이 부담이 아니고, 축 색이 틀렸을 때 각도를 트는 것도
자연스럽다. 차수 승격이 일어나도 왜 그런지 안다.
초보자용 가드레일은 오히려 방해가 되므로 두지 않는다.

### 1.1 프리핸드는 미룬다

획이 직선 세그먼트가 되고 손떨림은 버린다. `pts2d`는 계속 보존하므로
나중에 표현 계층으로 되돌아온다.

### 1.2 고유한 것은 둘뿐이다

| 부분 | 출처 |
|---|---|
| 스냅 | Rhino Osnap / SketchUp inference |
| 축 판정 | SketchUp (카메라 확정 후엔 자명) |
| 선 도구 | SketchUp (입력이 획일 뿐) |
| 뷰 관리 | Rhino 명명된 뷰 |
| 뷰포트·궤도·편집 | SketchUp |
| **초기 2D → 카메라 확정** | 고유 |
| **투시 차수 승격** | 고유 |

나머지는 검증된 메커니즘이므로 새로 설계하지 않는다.

## 5. 초기 확정 (개정)

### 5.1 소실점 후보

같은 방향 클러스터의 선 3개 이상이 한 점에서 만나면 후보.
**단 자동 확정하지 않는다** — L-A.6에서 획을 늘려도 축 오차가 개선되지 않음이
확인됐다(4→18→48→100획에서 7.40/10.04/10.09/4.53°, 단조 아님).

검출은 **초안**으로만 쓴다.

### 5.2 사용자 확정 — 가이드 선

소실점이 대개 화면 밖이므로 점을 끌 수 없다.
fSpy / Match Photo 선례대로 **축마다 가이드 선 두 개, 끝점 넷을 끈다.**

**동차 파라미터화를 쓴다**(`v = ℓ₁ × ℓ₂`, 나눗셈 없음). 소실점 위치로 다루면 가이드가
나란해질 때 발산한다(핸들 24px에 −360 → −37639). 동차 표현에서는 값이 유계로 남고
무한원이 자연스러운 극한이 된다(이론서 2.2절 c=0).

⚠ **재매개화는 발산을 고치지 않는다**(L-A.7이 측정, PITFALLS #24 — D-L2가 걸린 것과 같은 형태).
개정 2 원문은 "각도 차가 0에 가까워도 값이 튀지 않는다"로만 적어 발산이 해결된 것처럼 읽혔다.
갈라 적는다:

| | 각차 60° → 0.5° |
|---|---|
| **표현** | 위치 0.64 → 8115px(**12,600배**) 대 동차 각도 0.031 → 0.41°(**13배**) — 유계다 |
| **카메라** | f 상대 변화 0.0043 → 0.113(**26배**) · 축 방향 0.115 → **1.10°/px** — **여전히 발산한다** |

동차 표현이 실제로 주는 것은 **값이 유한하게 유지되어 스냅을 연속적으로 걸 수 있다**는 것뿐이다.
**실제 대응은 무한원 스냅**(각차 < `HOMOG_TOL.snap_deg` = 3°)이고 화면에 사유와 각차를 알린다.
각차 3°에서 0.39°/px이라 0.5° 예산의 78%다 — 그 아래는 조작이 불가능하다.
`vp_homog.json@34db7279`.

조정 중 실시간 피드백이 필수다 — 그리드와 이미 놓인 기하가 따라 움직이고
사용자가 눈으로 판별한다. **자동 검사가 원리적으로 불가능하므로**
(§5.3 참조) 이것이 유일한 판정 수단이다.

**임계는 축 오차 0.5°다.** ⚠ 개정 2 원문은 "약 1°"에 대역 0.079였고 **L-A.7이 정정했다** —
0.079는 `lift_gate`에서 가져온 **검출 오배정이 섞인** 값이고(PITFALLS #27), 같은 하네스
(`camera_gate.json@34db7279`)의 무오차 행은 **조용히 틀림 0.0673 · 형태 오차 중앙 0.0296**이다.
그 기준으로 0.48°에서 1.03배/2.07배, **0.96°에서 1.24배/3.67배**, 1.92°에서 7.5배/6.9배다.
통과선은 1.1배·2.1배이고 **두 지표를 다 낸다**(#28). 게이트 원문은 CLAUDE.md §2.

⚠ **"화면 환산 29~102px"은 소실점 좌표의 여유이지 핸들 여유가 아니다**(PITFALLS #29).
같은 배치에서 **핸들 예산**(축 오차 0.5°를 쓰기까지 핸들이 움직여도 되는 px, 각차 3~20°)은
가이드 **140px에서 0.29~1.01(서브픽셀)** · **300px에서 0.63~2.16** · **1250px에서 2.68~9.03**이다
(`vp_homog.json@34db7279`).

**§10의 단일 뷰포트가 이 예산을 늘렸다 — 다만 4배가 아니라 약 2배다**(L-B.1).
옛 좌우 분할은 캔버스 490×672라 가이드가 여백에 잘려 304~358px이 한계였고, 단일 뷰포트
(1280×675)에서는 **607.6 / 618.5 / 1233.3 / 1254.6 / 1256.8 / 1327.7px**가 나온다
(`stage_browser.json`).

⚠ **가장 긴 것으로 읽지 않는다.** `min_guide_ratio` 0.45가 요구하는 651px에 **여섯 중 둘이
미달**이고(잘림은 줄었을 뿐 없어지지 않았다), **카메라 정확도는 가장 나쁜 축이 정한다.**
짧은 쪽(≈600px)의 예산 1.28~4.33px을 옛 한계(≈300px)의 0.63~2.16px과 비교해 **약 2배**다.

⚠ **그 예산도 "핸들 하나만 움직인다"는 가정 위에 있다.** `vp_homog`의 섭동은 단일 핸들이고
사람은 **가이드 6개 = 핸들 12개**를 만진다. 넷이 독립으로 어긋나도 0.5°가 유지되는지는
안 쟀다 — **개별 핸들 예산이지 사용자가 도달해야 할 정밀도가 아니다.**

**⚠ L-B.2가 검출 초안으로 실제로 쟀고, 위 두 값보다 나쁘다**(`guide_budget.json@34db7279`).
**L-B.3(b)이 지지선 선택을 고친 뒤의 값**은 구도별 최소 예산이
3pt_yaw35_pitch15 0.95 · 3pt_yaw20_pitch25 **0.63** · 3pt_yaw50_pitch8 0.80 ·
2pt **0.465** · **1pt 0.547**px다. **1점 구도가 0.12 → 0.547px로 4.5배 나아졌지만 여전히 1px
미만**이고 58셀 중 15셀(26%)이 서브픽셀이다. 참 소실점을 넣은 1.3~4.3px은 **낙관값**이었다.
⚠ **옛 표(3.32 / 0.69 / 0.73 / 0.23 / 0.12, 31셀 중 9)와 행별로 비교하지 않는다** —
카메라가 서는 경우가 31 → 58로 늘어 **행마다 분모가 달라졌다**(#11).

**늘리기는 방향과 소실점을 안 바꾸고 지렛대만 늘린다**(카메라 불변). 이득은
**중앙 1.30배**이고, 요구 길이 미달 가이드가 347/540 → 249/540으로 준다.
⚠ **남는 미달은 그림이 아니라 캔버스 탓이다** — 늘린 뒤 길이는 언제나 그 방향의 캔버스 안
현이고, 1280×675에서 **수직 현의 상한은 588.18px**이라 요구 651.2px에 **원리적으로 못 닿는다**.
`min_guide_ratio`를 캔버스 짧은 변 기준으로 다시 정하는 것이 남은 일이다(DEFERRED).

**사람이 도달하는지는 여전히 표본 0**이다(AS-L9).

### 5.3 자동 판정이 불가능하다 (반증 기록)

계획서 초판의 전환 픽셀 차이와 교점 잔차는 **f 오차에 반응하지 않는다.**
둘 다 입사 관계에서 유도한 양이고 입사는 사영 불변이다.
f를 ±20% 틀리게 줘도 움직이지 않는다.

자동 판정 신호에서 제외한다. 사용자 눈이 판정 수단이다.

### 5.4 3D 올리기 — 한 번에 풀기

```
확정 순간 → 모든 획을 축별로 재분류   ← L에서는 그릴 때 전부 free다
         → 화면상 교점을 전부 찾는다
         → 교점 관계를 제약으로 A s = 0
         → 남는 자유도는 전역 배율 하나
```

앵커도 씨앗도 없다. 획의 3D 직선은 해석 평면 안에 있고 축이 방향을 정하므로
미지수가 획마다 하나다.

**검증** — 정확한 투영에서 오차 1e-6.

⚠ 개정 2 원문은 "**참 카메라에서 배치 0.995 / 조용히 틀림 0.079 / 형태 오차 중앙 0.026**"이었다.
**세 수치를 다 뺀다** — §5.2와 같은 정정이 여기에는 안 들어가 있었다(리뷰어 지적).

| 원문 | 왜 못 쓰나 |
|---|---|
| 배치 **0.995** | **최대 연결 성분 분모**다. L-A.4가 스스로 "이 분모는 판정을 공짜로 통과시킨다"고 적었다. 모집단 기준은 **0.885**다(PITFALLS #11) |
| 조용히 틀림 **0.079** | `lift_gate`의 값이고 **검출 오배정이 섞여 있다**. 같은 하네스 무오차 행은 **0.0673**이다(#27) |
| 형태 오차 **0.026** | `lift_gate` 값. `camera_gate` 무오차 행은 **0.0296**이다 — **같은 양이 두 숫자**로 돌아다녔다(#1) |

살아 있는 기준값은 **`camera_gate.json@34db7279`의 무오차 행 0.0673 / 0.0296** 하나이고,
§5.2와 CLAUDE.md §2가 그것을 쓴다. **다른 하네스의 값을 대역으로 가져오지 않는다.**

## 6. 차수 승격 (개정)

### 6.1 재계산 — 전부 다시

원본 `pts2d`가 보존되어 있으므로 새 카메라로 처음부터 올린다.
사용자 지정 스냅만 유지를 시도한다.

**뷰들의 카메라도 함께 갱신한다** — 각 뷰의 상대적 시점을 유지한 채
새 카메라 체계로 옮긴다.

### 6.2 판정 — 되돌리기가 주 수단

§5.3에 따라 재투영 잔차는 쓸 수 없다.
승격은 다른 카메라로 다시 푸는 것이라 **실제로 화면이 움직인다**
(§5.3의 전환 무변화와 모순이 아니다 — 그건 초기 확정에 한한 이야기다).

사용자가 즉시 보고 "1점으로 되돌리기"를 누른다.
임계를 정교하게 만드는 것보다 싸다.

대체 자동 신호 후보 둘(tiltDeg, 소실점 삼각형 f² 편차)을 시험하되,
사영 불변이 아닌 양인지 먼저 확인한다. 아니면 되돌리기만 쓴다.

> **2026-08-16 시험했고 둘 다 안 섰다**(L-C.3, `order_signal.json@34db7279`).
> **f² 편차는 자기참조 유형 3이다** — 주점을 수심으로 잡는 순간 세 f²가 같아지는 것이
> **항등식**이라, 틀린 소실점·둔각 삼각형·가짜 승격을 넣어도 편차가 전부 2.6e-16 이하다.
> 6.3의 "자유도 0"은 맞지만 **그 자유도는 주점을 세울 때 이미 소진된다.**
> ⚠ **이론서 6.4가 이미 그렇게 적어 두었다** — "세 조합 모두 같은 값을 준다(삼각형의 수심에
> 관한 고전 항등식)". **인접 절을 읽었으면 측정 전에 기각할 수 있었다**(#23).
> **`tiltDeg`는 사영 불변은 아닌데**(f×0.8~1.2에서 장면 중앙 1.414 → 1.228) **오승격을 못 가른다.**
> 오승격은 둘이다 — '승격할 장면이 아니었다'와 **'승격은 맞는데 소실점을 잘못 놓았다'**이고,
> 후자는 **참 팔과 같은 구도**라 교락이 없는데 **구도별 판별력이 0.015 · 0.074 · 0**이다.
> 시드 부호도 갈린다(여섯 중 둘). 전자와의 합산 0.1979는 **구도 간 비교**라(가짜 팔이 2pt 한
> 구도뿐이다) 구도 효과가 섞여 있다.
> ⚠⚠ **그 실패는 신호의 것이지 픽스처의 것이 아니다** — **참값을 고정 게이지로 재면 판별력이
> 가짜 승격 0.9694 · 틀린 VP3 0.5446**으로 둘 다 0.5를 넘는다. 자기 게이지 값은 최소제곱이
> 전역 배율을 없앤 뒤의 수이고 **§9.1이 '사용자가 보는 오차'라 적은 배율 성분을 지운 것**이다.
> 틀린 VP3의 축 각오차는 **중앙 5.59°로 §5.2 임계 0.5°의 11배**다.
> `tiltDeg`가 **f 오차와 축 오차를 한 수에 섞는다.**
> **그러므로 되돌리기만 쓴다 — 이 절이 적어 둔 두 갈래 중 하나이고 우회가 아니다.**
> ⚠ 다만 **'잴 것이 없어서'가 아니다** — 관측 가능한 신호를 아직 못 찾은 것이고 여지가 크다.
> 그 되돌리기는 L-C.2가 만들었다: **차수를 명시한 되돌리기**(`N점으로 되돌리기`, 소실점과
> 기하를 함께 되돌린다)와 **승격이 잃은 것의 표시**(내려간 획 · 끊긴 스냅).

## 7. 실시간 그리기 (개정)

카메라 확정 후.

```
획 시작 → 첫 점이 스냅 → 3D 확정
그리는 중 → 축 판정 → 커서 위치에서 끝점 3D 결정
          → 축 색, 미리보기 선, 스냅 하이라이트
획 종료 → 확정, 세그먼트 생성, 교차 갱신
         → 스냅 실패 시 2D 레이어로 (§9)
```

**뷰포트는 하나다.** 궤도 회전은 카메라 조작이고 좌표계는 계속 같다.
**소실점은 잠긴다.** 차수 승격만이 카메라를 바꾼다.

## 9. 뷰 시스템과 2D/3D 레이어 (신규)

### 9.1 두 레이어

```
2D 레이어 : 아직 공간에 정의되지 않은 획
3D 레이어 : 정의된 획
```

**미배치는 실패가 아니라 대기 상태다.** 조건이 갖춰지면 승격한다.
초기 확정이 이미 이 방식이므로 예외가 없어진다.

**승격은 연쇄한다.** 새 획이 3D 기하에 붙으면, 그 획과 만나던 2D 획들도 함께 결정된다.

> 아래 수치는 전부 `promote.json@34db7279`이고 **조건은 참 카메라**다(리뷰어 [16]).
> 앱의 `promoteChain`은 초안·조정 카메라 위에서 돌고 **그 조건은 안 쟀다.**
> 초안 카메라의 축 오차는 임계의 18~28배이므로(§5.4) 아래 수치는 **상한으로 읽는다.**

⚠ **§5.4의 일괄 풀이를 재사용하는 경로의 "회수 0"은 측정이 아니었다**(PITFALLS #32).
대기 1904획이 **솔버에 닿기 전에 거름에서 전부 걸렸다**(`축이 미분류다` 1116 ·
`구조에 이어지지 않았다` 620 · `no_committed_geometry` 168 = **1904, 남김없이**).
**입력이 0인 실행의 결과는 기전에 대한 정보가 0이다.**

**축을 주고 다시 돌리니 그 기전이 실행되고 크게 회수한다.**
오라클 축에서 입력 1904 · **솔버가 놓은 것 1154** · 채택 **1154(60.6%)**다.
즉 §9.1의 일괄 기전은 **반증된 적이 없고**, 막고 있던 것은 기전이 아니라 **축 판정**이다 —
L-B.3(a)·L-B.4가 지배항으로 지목한 그것이다.
⚠ **앵커 720과 직접 견주지 않는다** — 그것은 실제 축 라벨이라 **기전 차이와 축 정보 차이가 섞인다.**
축을 맞춘 앵커 대조군은 **804/1904**이고 일괄이 그보다 **1.44배** 많다(804 대 720이 축 정보의 몫이다).
동작점을 헐겁게 해도 **축을 맞춘 채로** 앵커는 968이라 1154에 못 미친다
(⚠ 오라클 축에서는 `axis_deg`가 아무 효과가 없다 — 흔드는 것은 **스냅 반경 하나**다).
⚠ **오라클은 상한이다.** 연쇄가 실제로 붙인 축 라벨로는 **24/966**뿐이다.

⚠ **그러나 일괄은 더 많이, 더 틀리게 놓는다.** **추정기를 맞춰**(셋 다 자기 게이지) 보면
일괄 **558/1154 = 0.484** · 축을 맞춘 앵커 **269/804 = 0.335** · 확정 **874/2416 = 0.362**다.
일괄만 나쁘다. ⚠ **축을 맞춘 앵커 0.335는 확정 0.362와 구분되지 않는다**(비 0.925는 시드 밴드 안이다).
**§9.1이 살아난 것은 개수 기전으로서이지 품질 기전으로서가 아니다.**

**지금 구현에서 실제로 회수하는 것은 앵커다** — 대기 획의 **시작점이 새로 놓인 기하에 붙으면**
§3·§7의 실시간 경로가 그 획을 놓는다(**1회차** 720/1904 = 37.8%, **연쇄 포함** 938/1904 = 49.3%).
**승격은 "다시 푸는 것"이 아니라 "앵커가 생기는 것"이다.**

**연쇄는 실제로 일어나고 이 픽스처에서 수렴한다.** 2회차 **192** · 3회차 **25** · 4회차 **1**로
추가 **218**이고 상한 8회에 도달한 장면은 **0/338**이다(대기 0인 22장면 제외). 합계 **3354/4320**.
⚠ **장면당 획이 12개**(상자 하나의 모서리)라 연쇄 깊이 4는 **픽스처가 정하는 상한에 가깝다** —
"수렴한다"를 일반 명제로 읽지 않는다. 상자 둘 이상은 안 쟀다.

⚠ **승격이 더 내는 오차는 형태가 아니라 배율이다.**
같은 720획을 고정 게이지로 재면 cut 0.2 **392/720(0.544)**, **자기 게이지**로 재면 **286/720(0.397)**이고
확정은 자기 게이지로 **874/2416(0.362)**이다. 자기 게이지 배수는 **시드별 0.865~1.150으로
1을 가로지르므로 그 격차는 결론이 아니다**(#14) — 고정 게이지 배수는 시드 여섯 전부 1.20~1.57이다.
즉 **형태만 보면 회수와 확정이 구분되지 않고, 차이는 전부 확정된 틀과 배율이 안 맞는 데서 온다.**
앱이 회수 획에 배율을 다시 안 맞추므로 **그 배율 어긋남이 사용자가 보는 오차다.**
⚠ 다만 **꼬리는 자기 게이지에서도 나쁘다**(p90 0.9144 대 0.4468, ≈2배).
**cut 0.2 비율 · 중앙 · p90의 배수가 서로 다르므로 "격차 N배"를 한 수로 적지 않는다.**
"미배치는 대기다"는 **개수 회수에 대해서만 참**이고 "나중에 더 정확히 놓인다"는 뜻이 아니다.

⚠ **회수율도 회수 품질도 한 값이 아니다.** 끝점 잡음으로 가르면 회수율이
**162/227(0.71) → 163/781(0.21)**(연쇄 포함이면 0.75 → 0.30)이고,
**구도로 가르면 조용히 틀림이 3pt 52/163(0.32)에서 1점 구도 90/93(0.968)까지 간다**
(같은 층의 **확정**은 82/412과 268/422이다 — 층을 맞춰야 배수가 층 효과와 안 섞인다).
**1점 구도는 회수한 것의 거의 전부가 조용히 틀리고 연쇄도 0이다** — 자유도가 가장 적고
승격이 가장 위험한 자리다.
그리고 37.8%는 `axis_deg` 12 · 반경 0.05라는 **동작점 하나의 통과율**이다(스윕 0.25~0.49,
개수와 조용히 틀림이 단조로 맞바뀐다). 실획이 어느 대역인지는 표본이 0이다(AS-C1).

떨어진 곳에 그린 덩어리도 자기들끼리 2D로 쌓이다가 연결되는 순간 전부 올라간다.

### 9.2 뷰 — 2D 획의 소유자

```
View     { id, name, camera, createdAt }
Stroke2D { pts2d, viewRef }
Stroke3D { segment, ... }        // 뷰 무관
```

라이노의 명명된 뷰와 다른 점: **뷰가 2D 획을 소유한다.**
자기 뷰로 돌아가면 제자리에 보이고, 다른 뷰에서는 숨거나 흐려진다.
뷰를 지우면 그 안의 미배치 획도 함께 사라진다.

**승격되면 뷰 소속이 없어진다.** 어느 뷰에서든 보인다.

### 9.3 뷰 생성

카메라 확정 시 첫 뷰가 자동 생성된다.
궤도를 돌려 **새 각도에서 실제로 획을 그리면** 그 시점이 새 뷰로 등록된다.
돌릴 때마다 만들지 않는다 — 뷰가 넘친다.

이름을 붙일 수 있다("정면", "우측 상단"). 라이노 방식 그대로.

### 9.4 표시

2D 획을 3D와 **약하게 구분**한다. 회전하면 어차피 드러나므로 미리 알리는 편이
낫고, 지나치게 강조하면 결함처럼 보인다.

다른 뷰의 2D 획은 숨긴다. 화면이 복잡해지지 않는다.

### 9.5 사용자 지정

영원히 안 올라가는 획이 쌓일 수 있다.
"이 획은 저 면 위에 있다" 수준의 지정 경로와, 지우는 경로를 둔다.

> **2026-08-16 L-D.1이 절반만 했다.** **지우는 경로는 섰다**(`고치기` 도구 — 클릭 선택 ·
> Delete · 실행취소. 스냅 대상도 함께 줄어든다).
> ⚠ **지정 경로는 "면"이 아니라 "축"이다** — 면 생성(§6)이 범위 밖이라 줄 수 있는 것이
> **방향**뿐이다. 둘은 같지 않다: 면 지정은 획을 **평면에 가두고** 축 지정은 그러지 않는다.
> ⚠⚠ **그리고 축 지정이 옳은 답이 아닐 수 있다.** `face_diagonal.json@34db7279`가
> **"축으로 배정된 사선이 놓인 것은 회수가 아니라 조용히 틀린 배치다"**라고 적었고

> **§9.5가 원한 것은 그쪽일 가능성이 크다.**
> **2026-08-16 결론(D-L28)**: 기존 원장만으로 결론했다 — **면 대각선에 대해서는** 축 지정이

> ⚠ **그 원장은 면 대각선 120개만 본다** — 축이 미분류라 대기 중인 획(1116)에 대해서는

## 10. UI 재작성 (신규)

### 10.1 왜 새로 만드는가

현재 UI는 세 번의 접근 전환을 거치며 폐기된 전제 위에 덧대어져 있다.

| 요소 | 상태 |
|---|---|
| 좌우 분할 (캔버스 \| 3D 뷰) | 폐기 — 뷰포트 하나 |
| 평면/투시 프레임 탭 | 폐기 |
| "여기서 그리기" 토글 | 폐기 — 뷰 시스템으로 대체 |
| 축1/축2/축3 점 찍기 | 대체 — 가이드 선 |
| 고치기 도구 | 폐기 — 스냅으로 대체 |
| 치수 패널 | 폐기 — 무차원 |

남는 것이 거의 없다. 고치면 폐기된 구조의 흔적이 남는다
(평면 파선 투영 같은 죽은 코드가 계속 나온 이유).

### 10.2 범위

**`web/src/ui/`만 교체한다.** 다음은 그대로 쓴다.

`canvasFrame`(dpr 규약), 잉크 캡처, Three.js 씬·워커,
`lift.ts`, `vpDetect.ts`, 카메라 수학, 저장·내보내기.

### 10.3 구성

```
┌────────────────────────────────────────┐
│                                        │
│      (2D 잉크 + 3D 씬, 단일 뷰포트)     │
│                                        │
├────────────────────────────────────────┤
│ [뷰 목록] [스냅] [축고정] [실행취소]     │
└────────────────────────────────────────┘
```

**초기**: 빈 화면. 그리면 2D로 쌓인다. 소실점 후보가 잡히면 가이드가
나타나고, 조정 후 확정.

**확정 후**: 그리드가 깔리고 실시간 스냅·축 색이 동작한다. 궤도 회전 가능.

**뷰 목록**: 사이드. 새 각도에서 그리면 뷰가 생긴다.

## 12. 위험

**L-B 게이트가 실질 판정이다.** 실시간 스냅이 손 획에서 붙는지,
미리보기가 사용자 판단에 쓸모 있는지는 만들어봐야 안다.
자동 측정이 어렵다 — 스냅 성공률은 재지만, 색이 틀렸을 때 각도를 트는지는
써봐야 안다.

**AS-L9 미측정.** 사람이 축 오차 **0.5°**(§5.2 정정) 안으로 맞추는가.
대리값은 드래그 범위가 아니라 **핸들 예산**이고(#29), 가이드 길이에 달렸다 — 140px에서 0.29~1.01,
300px에서 0.63~2.16, 1250px에서 2.68~9.03px이다(§5.2). **새 뷰포트의 짧은 가이드(≈600px)에서 1.28~4.33px**이고
이것이 §5.2의 실제 한계다. 그나마 **핸들 하나만 움직인다는 가정** 위의 값이다.
L-D 종단 검증에 시나리오를 넣되, 자동화가 어려우면 실사용 대기로 둔다.

**실획 0.** 이 접근은 끝점 오차 의존이 크게 줄어 영향이 작아졌으나,
스냅 반경과 축 판정은 여전히 실획에 달려 있다.

**뷰가 넘칠 가능성.** 자동 생성 조건(실제로 그렸을 때만)이 충분한지 미확인.
