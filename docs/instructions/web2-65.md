# §1 칠 성능 — 이 라운드의 본체

## 진단 — 코드에서 확인했다 (추측 아님)

`app/render3d.ts`의 `syncPaintTex`:

```js
const key = `${app.docVersion}|${getHatchMode()}|${draftOnlyTargets(app)}`
if (key === paintKey) return
paintKey = key
for (const e of paintTexes.values()) {
  r.paintGroup.remove(e.mesh)
  e.mesh.geometry.dispose()
  ;(e.mesh.material as THREE.Material).dispose()
  e.tex.dispose()
}
paintTexes = new Map()          // ← 전부 버린다
```

그리고 `gatePaintTex`가 항목마다:

```js
const strokes = paintStrokesOf(app, e.faceId, e.side)   // ← 그 면의 «획 전부»
bakeFaceTex(e.canvas, rf, e.box, lv, strokes, ...)      // ← 전부 다시 굽는다
e.tex.needsUpdate = true                                 // ← 텍스처 «전체» 업로드
```

**그래서 이렇게 된다.**

```
획 하나를 커밋
  → docVersion 증가
  → 모든 (면, 쪽)의 메시·기하·재질·텍스처를 «폐기»
  → 전부 다시 만든다
  → 면마다 그 면의 획 «전부»를 mypaint 도장 루프로 다시 굽는다
  → 각각 GPU에 «통째로» 업로드

N번째 획 = N개 재굽기.  세션 전체로 O(N²).  면 수만큼 곱해진다.
```

⚠ 그리고 **`docVersion`은 어떤 문서 변경에도 오른다** — 선 하나를 옮겨도, 치수를 고쳐도
칠이 전부 다시 구워진다.

## ⚠ 착수 전 — D-2로 값을 먼저 낸다

면 하나에 획을 **1 · 10 · 30 · 60**개 그으면서 값으로 재라.

```
(a) 커밋 한 번의 시간(ms)          → 획 수에 비례하는가
(b) 그때 재굽힌 «획 수»            → 새 획 하나인가, 전부인가
(c) 텍스처 업로드 바이트           → 전체인가 부분인가
(d) 궤도 중 프레임 시간            → 칠이 많을 때
(e) 면 셋에 각각 20획일 때의 (a)   → 면 수만큼 곱해지는가
```

**이 값이 수리 전 판(pre 원장)이고, 게이트가 그것과 대조한다.**

## 고칠 것 다섯

```
① 캐시 키를 «면·쪽 단위»로
   그 면의 그 쪽 획 목록 서명(id + 그 획의 판)이 키다. 문서 전체가 아니다
   → 선을 옮기거나 치수를 고치면 칠을 «안» 다시 굽는다

② 항목을 폐기하지 마라
   메시·기하·재질·텍스처를 재사용한다. 없어진 (면,쪽)만 빼고 새로 생긴 것만 더한다

③ ⛳ 누적 — 새 획은 «얹기»만 한다
   전량 재굽기는 «정본이 바뀔 때만»:
     획 삭제·수정 · 해상도 단계 변경 · 브러시 재바인딩 · 재료/해칭 변경 · 면 경계 변경
   ⚠ 이건 62의 «획 버퍼 → over» 2단 합성과 «같은 것»이다. 새 개념이 아니다
   ⚠ 59의 미리보기가 이미 그 길이다(base 사본 → draft 덧그리기). 커밋도 같은 길로 보내라

④ 부분 업로드
   더티 사각만 올린다(three.js의 텍스처 갱신 범위). 1024² 전체를 매번 올리지 마라

⑤ 메모리 상한과 LRU
   면 20 × 쪽 3 × 1024² RGBA = 240 MB. 상한을 정하고 넘으면 «안 보이는 면»부터 버린다
   (버린 것은 다시 필요해지면 다시 굽는다 — 파생이므로 안전하다)
```

## 게이트

```
① ⛳ 픽셀 항등              누적으로 그린 결과 == 전량 재굽기 결과. sha 항등 · 도구 전수
                           «빠른데 다른 그림»이면 안 된다. 이것이 중심 게이트다
② 커밋 시간이 평평하다      획 1·10·30·60에서 커밋 한 번의 시간이 ±20% 안
                           (pre 원장의 비례와 대조 — 개선 배수를 값으로)
③ 재굽힌 획 수 = 1         새 획 하나만 굽는다. 값으로
④ 다른 변경이 칠을 안 건드림  선 옮기기·치수 수정에서 재굽기 0회
⑤ 무회귀 트리거가 «산다»    획 삭제·되돌리기·해상도 단계·브러시 재바인딩·재료 변경에서는
                           «다시 굽는다» — 전수로 확인. 하나라도 빠지면 낡은 그림이 남는다
⑥ 반증(D-3)                누적을 끄면 pre의 O(N)이 돌아온다
⑦ 메모리                   상한이 지켜진다 · 상한에서 버린 뒤 다시 보면 같은 픽셀
⑧ 프레임                   획 60 · 면 3 장면의 궤도 프레임(pre와 대조)
```

**⛳ 사진**: `web2/shots/65-perf.png` — 획 수 대 커밋 시간 그래프(pre vs post).
숫자만이 아니라 **그림으로** 보이게 하라.

무회귀: 50·55·56·59·62·63·64 게이트 전부 · `roundtrip43` ②.

- ⛔ **해상도를 낮춰서 빠르게 하지 마라.** 그건 속임수다. 게이트 ①이 그것을 잡는다

# §2 패널 다듬기 넷 — 작다

64의 사진(`64-panel.png`)에서 보이는 것. 전부 §1과 다른 코드다.

```
① 패널이 오른쪽 세로 툴바에 «잘린다» — 브러시 이름이 `liner · dee...`로 끊긴다
   자리를 다시 잡아라. 작도 툴바와 칠 패널이 둘 다 오른쪽이라 답답하다
② 즐겨찾기 여섯 칸이 «아이콘 + 잘린 이름»이다
   64 §2 규칙 ①이 「자국 견본으로. 이름만으로는 안 된다」였는데 거기만 안 지켜졌다
   여섯이 다 비슷한 연필 아이콘이라 구분이 안 된다 → «그 브러시의 실제 자국»으로
③ `100% Opaque` 같은 mypaint 프리셋 이름이 그대로 나온다
   사람이 읽을 이름으로 사상하라. 원 이름은 도움말에 남긴다
④ 이름이 잘리는 칸 전수 — 잘리면 이름이 아니다
```

**게이트**: 즐겨찾기 여섯 칸이 서로 «픽셀로» 다르다 · 화면 폭 둘(800·1200)에서 잘린 글자 0 ·
34-0 표 다시(자리가 바뀐다).
