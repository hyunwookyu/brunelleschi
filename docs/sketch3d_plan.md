## 1. 제품 정의

손으로 그린 투시도가 그대로 3차원 오브젝트가 된다.

**핵심 원칙: 획을 버리지 않는다.**
직선을 추출해 면을 만드는 것이 아니라, 그린 곡선 그대로가 3D 공간의 곡선이 된다.
손떨림도 전부 남는다. 시스템이 판정하는 것은 **방향뿐**이다.

```
2D 획 (손떨림 포함)
  → 방향 판정 (이 획은 어느 축인가)
  → 앵커 결정 (시작점의 3D 위치)
  → 각 점 역투영
3D 획 (손떨림 그대로, 축을 감싸며 흔들림)
```

한 시점에서 그림이 완성되면 회전·이동한 뒤 새 시점에서 다시 투시도로 보고
이어 그린다. 이 왕복이 무한히 반복된다.

### 1.1 이전 접근과의 차이

| | 이전 | 이번 |
|---|---|---|
| 획의 운명 | 직선으로 대체, 폴리곤화 | 그대로 유지 |
| 스냅 대상 | 형태 (점을 옮김) | 방향 (축만 판정) |
| 결과물 | 압출 볼륨 (메쉬) | 3D 곡선 집합 |
| 손떨림 | 제거할 노이즈 | 보존할 표현 |
| 종횡비·치수 | 추론 대상 | 관심사 아님 |

**추론이 사라진다.** 카메라가 확정되면 나머지는 계산이다.
이전에 막혔던 것들(2점 종횡비 상대폭 0.894, 꼬리 실패 20.5%, 사전 판정 불가)은
전부 "완성된 스케치에서 형태를 역산"하려 해서 생긴 문제였고, 그 작업 자체가 없어진다.

### 1.2 사용자 전제

투시도 숙련자. 소실점을 향해 정확히 긋는다.
따라서 시스템이 형태에 개입할 이유가 없고, 보정은 다음 수준으로 제한한다.

- **한다**: 획의 축 배정 (6°를 0°로 만드는 게 아니라 "이 획은 X축"이라 판정)
- **한다**: 끝점 접합 (두 획의 끝이 몇 px 안이면 같은 점으로)
- **안 한다**: 획을 직선으로 펴기
- **안 한다**: 중간 점 이동

### 1.3 범위

**되는 것**
- 투시도를 그리면 3D 곡선이 된다
- 회전·이동 후 새 시점에서 이어 그리기
- 축을 벗어난 획도 처리 (아래 4.3)
- 벽 두께 등은 사용자가 평행선을 그으면 된다. 시스템이 의미를 알 필요 없음

**안 하는 것**
- BIM 요소 (층·창·문의 의미론)
- 정밀 치수 작업
- 렌더링, 재질

### 1.4 배포

GitHub 공개, 웹 기반, 경량. PWA로 오프라인 동작.
빌드 없이 정적 호스팅 가능한 형태를 지향한다.

## 2. 참조 구현

`notebysebas/sketchbook-v8` (Sketch3D). three.js r128, 단일 HTML 12,833줄, PWA.

### 2.1 확인된 것

**획 보존이 실제로 동작한다.** raw 모드에서 trim을 완전히 끄고
(`_trimThresh = -1.1`) 점열 전체를 튜브 메쉬로 만든다.
직선화 없이도 3D 형태로 읽히고, 브라우저 성능이 충분하다.

이것이 이 계획의 실현 가능성 근거다.

### 2.2 구조적 차이

그 도구는 **3D 공간에 평면을 배치하고 그 위에 그린다.**

```js
function s2w(px,py){
  drawRC.setFromCamera(ndc, activeCam());
  if(!surfMesh) return null;
  if(surfType==='none') return null;
  var shits = drawRC.intersectObject(surfMesh,false);
  return shits.length ? shits[0].point.clone() : null;
}
```

레이캐스트가 표면에 맞아야만 점이 생긴다.
소실점, 축 판정, 투시 기반 카메라 복원이 전혀 없다.

**이번 계획은 그림 자체가 공간을 정의한다.** 평면 배치가 없다.

다만 구조적으로는 같은 자리다 — 화면 점 하나를 3D로 올리려면 제약 하나가 필요하고,
그 출처가 "배치된 평면"에서 "축 방향 + 앵커가 만드는 직선"으로 바뀔 뿐이다.

### 2.3 라이선스 — 코드 복사 금지

**LICENSE 파일이 없다.** 소스에 저작권 표시도 없다.
라이선스 없는 공개 저장소는 기본적으로 모든 권리 유보이며,
포크·수정·배포가 불가하다.

**참조는 동작 확인 용도로만 한다. 코드를 복사하지 않는다.**
접근과 아이디어는 저작권 대상이 아니므로 직접 구현한다.
필요한 것들이 표준적이라 복사할 이유도 없다.

- 튜브 메쉬 — three.js `TubeGeometry` 내장 (MIT)
- 속도 기반 굵기 — 점 간격에서 계산
- undo/redo, 레이어, 지우개 — 일반적 구조
- PWA — manifest + service worker 표준

## 3. 카메라 확정

첫 그림에는 카메라가 없으므로 소실점 정보가 필요하다.
회전한 뒤에는 카메라를 정확히 알므로, 이것은 **최초 1회 부트스트랩**이다.

### 3.1 제약 누산기

입력 방식을 고정하지 않는다. 여러 제스처가 같은 누산기로 수렴한다.

| 제스처 | 기여 제약 |
|---|---|
| 점 찍기 | 소실점 하나 확정 |
| 선 하나 긋기 | 그 소실점이 이 직선 위에 있다 |
| 선 두 개 이상 | 교점 클러스터 → 소실점 |
| 지평선 긋기 | 수평 소실점들이 이 위 + 주점 y |
| 렌즈 슬라이더 | f |
| 이후 그리는 획 | 자기 축의 소실점에 계속 투표 |

"찾아내기"와 "정의하기"의 구분이 없다.

### 3.2 해 계산

이론서(docs/perspective_theory.md)의 닫힌 해를 쓴다. 1-ter에서 검증 완료(잔차 0).

| VP 개수 | 방법 | 절 |
|---|---|---|
| 3 | 주점 = 소실점 삼각형의 수심, f² = \|PVᵢ\|·\|PHᵢ\| | 6.3, 6.4 |
| 2 | 지평선 → 주점 y, f² = \|PV₁\|·\|PV₂\| | 6.2 |
| 1 | 소실점 = 주점, f는 설정값 | 5.3 |

과잉 결정 시 최소제곱, 잔차 표시.

### 3.3 유효성 검사 (실시간)

- **3점 예각 조건** (6.5절): 둔각이면 f² < 0. 물리적으로 존재하지 않는 카메라.
  점을 끄는 동안 즉시 붉게 표시
- **화각** (18.4절): d < 0.5W면 90° 초과 경고

### 3.4 상태 표시

이론서 5.3절의 자유도 회계를 화면에 그대로 보인다.

```
소실점 1개  →  1점 투시 · f 자유          [렌즈 24mm]
소실점 2개  →  2점 투시 · 주점x/f 중 1자유  [주점=화면중심]
소실점 3개  →  확정
```

**부분 확정 상태에서도 그릴 수 있다.**
1점에서 f가 자유여도 화면평행 방향(폭·높이)은 축소가 없으므로(7.7절)
그 축의 획은 즉시 배치된다.

### 3.5 프리셋

실내 1점 24mm / 실내 2점 35mm / 외부 2점 50mm / 외부 3점 앙각.
기본값으로 두고 필요할 때 조정. 시작 마찰을 없앤다.

### 3.6 투시 그리드

카메라가 정해지면 캔버스에 옅은 지면 격자와 축 가이드를 깐다.
그리기 전에 축 방향이 보이므로 판정이 예측 가능해진다.
건축가가 구축선을 먼저 긋고 그리는 방식과 같다.

### 3.7 소프트 락

그리는 동안 획 투표로 카메라가 미세하게 움직이면 이미 배치된 기하가 흔들린다.
확정 전까지 자유 갱신, 확정 후 잠금.
사용자가 명시적으로 풀면 재조정 가능하고, 그때 기하가 따라 움직이는 것은
예상된 동작이다.

### 3.8 화면 밖 소실점

2점 투시에서 흔하다. 캔버스보다 넓은 좌표계, 축소 뷰, 또는 가장자리 방향 핸들.
무한대는 명시적으로 표현한다 — c=0인 축 (2.2절).

## 4. 획 → 3D

이 계획의 핵심이다.

### 4.1 방향 판정

획 전체가 하나의 축에 배정된다. 개별 점은 그 축을 중심으로 흔들린다.

**판정은 점-직선 거리로 한다.** 획의 대표 방향(시작-끝 또는 최소제곱 직선)을
연장해 각 소실점을 지나는지 검사한다. 각도 추정보다 강건하다 —
끝점 오차의 영향이 작고 클래스가 서로 멀다.

분류 대상:
- VP1 / VP2 / VP3 방향
- 화면평행 (c=0, 축소 없음)
- 면 위 사선 (아래 4.3)
- 미분류

**크게 휜 획의 처리** — S-2에서 결정했다(DECISIONS D-S2: 곡률 임계 초과 시 미분류).
후보: 최소제곱 직선으로 배정 / 곡률 임계 초과 시 미분류 / 사용자 지정.

**한 획에 여러 축** — S-2에서 결정했다(DECISIONS D-S3: 검출해 미분류, 분절 안 함).
**실획 위반율 0.699**(Quick,Draw 낙서 기준 상한) — AS-6, `stage0/out/one_stroke_one_axis.json`.
후보: 방향 급변점에서 분절 / 축마다 끊어 그린다고 가정.
사용자가 숙련자라는 전제상 후자가 성립할 가능성이 있으나 확인 필요.

### 4.2 위치 결정 (앵커 체인)

방향만으로는 깊이가 정해지지 않는다.

1. **씨앗**: 첫 획의 시작점. 지면 접촉 가정(Z=0) 또는 사용자 지정
2. **전파**: 그 점에서 축 방향으로 광선-직선 최근접점
3. **교차**: 기존 획과 만나는 지점이 새 앵커
4. 반복

**연결된 것만 배치된다.** 떠 있는 획은 깊이가 미결정이며,
가장 가까운 기존 기하에 붙이거나 사용자 지정을 요구한다.

> **S-3 정정**: 지면은 카메라 좌표계의 `y = const`가 **아니다** — 그것은 카메라가 수평일 때만
> 맞고 3점 투시에서는 기울어 있다. 지면 평면은 **수직축(vps[2]) 방향이 법선**이며
> 눈높이 게이지는 `geom3d.EYE_HEIGHT` 한 군데에만 둔다(격자와 씨앗이 같아야 한다).
>
> **3번(몸통 접합)은 선택이 아니라 필수다.** 끝점끼리만 이으면 끝점 겨냥 오차가 그림 대각의
> 2%일 때 **47%가 앵커를 못 찾는다**(참 축·`facing` 조건, `endpoint_only_control`).
> 몸통 접합을 넣으면 **11%**로 줄고, 붙는 위치는 선분 보간으로 잡는다
> (가장 가까운 표본점을 쓰면 점 간격의 절반이 앵커 오차가 되어 체인을 타고 증폭된다).

### 4.3 축을 벗어난 획

어떤 VP도 향하지 않는 획은 세 경우다.

- **이미 정의된 면 위에 있음** — 면 + 시선 광선 = 3D 점이 유일하게 결정된다.
  방의 대각선, 경사 지붕 처마, 계단 코 선이 여기 해당
- **경사 소실점** — 이론서 15.1절: 경사 VP는 대응 수평 VP의 바로 위/아래.
  검출이 어렵지 않다
- **진짜 자유 곡선** — 임시 평면(시선 수직)에 놓고 사용자가 나중에 조정

첫 번째가 중요하다. 이전 측정에서 비직교 획이 52.6%였는데
상당 부분이 여기서 회수된다.

> **정정(리뷰어)**: 52.6%는 **검출기 오탐이 섞인 값**이다. 오탐을 바닥으로 보정하면
> house 0.29 / castle 0.36이다(assumptions V-z). 같은 표본의 곡선 획 26.5%와도 분리돼 있지 않다.
> S-6의 회수율 분모는 **오탐 보정 후 비직교 직선 획**으로 정의하고 0.29~0.36을 비교 기준으로 쓴다.
>
> **경사 소실점 "검출이 어렵지 않다"는 근거 없는 예상이다.** 이론서 15.1은 경사 VP가
> 대응 수평 VP의 바로 위/아래에 있다고만 말한다 — 그 둘이 **가장 가까운 경쟁자**라는 뜻이기도 하다.
> W-2는 "짧은 선은 틀린 VP에도 아주 잘 맞는다"를 측정했다. S-6이 잰다.

### 4.4 떨림을 담을 평면

축 방향 직선 L이 정해지면, 손떨림을 담을 평면은 L을 포함하는 평면 중 하나여야 한다.

> **S-3에서 결정했다(DECISIONS D-S8). 후보가 둘이 아니라 셋이었다.**
> 어느 평면을 골라도 **그린 카메라에서의 화면 이미지는 똑같다** — 각 점이 자기 광선 위에
> 놓이기 때문이다. 평면 선택이 정하는 것은 **깊이**뿐이고 차이는 **돌린 뒤에야 보인다.**

- **눈을 지나는 평면 — 후보가 아니다.** L과 눈을 함께 담는 평면은 화면에 **직선 하나**로
  맺히므로 축을 벗어난 점(=떨림)의 광선이 원점에서만 만난다. 한 점도 놓이지 않는다.
  구판의 "시선을 포함하는 평면"을 글자 그대로 읽으면 배치가 불가능하다.
- **`sight`** — L과 **광축 방향**을 담는 평면(구판 첫째를 성립하게 읽은 것).
  평면이 시선과 거의 나란해 조건수가 나쁘다 — 광선이 스쳐 안 만나는 획이 생겨 배치율이 낮고
  (참 축 0.9806 vs `facing` 1.000), 연쇄 깊이 오차가 7배로 자란다. 기각.
- **`screen`** — 앵커를 지나는 화면 평행 평면(구판 둘째). **L을 담지 못한다**.
  획이 깊이로 들어가지 않는다. 이것이 §4.5의 미리보기 평면이다. 기각.
- **`facing` — 채택.** L을 담되 **시선에 가장 정면으로** 서는 평면.

**대표 조건**(판정 통과 · 끝점 겨냥 오차 2% · skew 0.12 · medium, 중앙값):

| 평면 | 축 각도° | 모서리 오차 | 깊이 오차 |
|---|---|---|---|
| `sight` | 13.31 | 0.2412 | 0.1385 |
| `screen` | 34.06 | 0.3644 | 0.2021 |
| **`facing`** | **2.14** | **0.0597** | **0.0277** |

이 순위는 끝점 오차 0·2%와 f 오차 ±20%까지 **전 조건에서 유지된다**.
단 **비교는 참 카메라 조건**이다 — f 20% 오차만으로 모서리 오차가 0.145까지 오르므로
카메라 설정 오차가 평면 선택의 차이와 같은 대역이다(AS-9).

**떨림비는 근거에서 뺐고 주장도 좁혔다.** L을 담는 평면 족을 각도로 훑어 보니 네 채널
(떨림비·모서리 오차·축 각도·깊이 오차)이 **전부 0°에서 극값이고 순위가 완전히 같다** —
관측은 넷이 아니라 하나이며, 떨림비는 정의의 귀결이다. 그리고 **±20° 안에서는 구분되지 않는다**
(모서리 0.0165 vs 0.0171, 유효 자릿수 2자리 밖). 따라서 **족 안에서 `facing`을 특정하는 근거는
없고**, 채택이 지지되는 것은 **극단의 기각**이다 — `sight`는 족의 79.6°로 전 채널 6배 나쁘고,
`screen`은 족 밖이다. `facing`은 최적 구간의 **정준 원소**로 고른 것이다.

측정: `stage0/out/wobble_plane.json`. 판단 기준은 회전 후 자연스러움이었다.

### 4.5 호출 단위 문제

포인터 이벤트마다 점이 하나씩 들어오는데, 축 판정은 획 전체를 봐야 한다.

```
그리는 중 : 임시 평면(시선 수직)에 놓고 미리보기
획 종료   : 축 판정 → 전체 점열 재투영 → 확정
```

`finStroke()`에 재투영 단계가 들어간다.

> **S-3 측정 결과**: **그린 카메라에서는 두 평면의 화면 이미지가 같다**(각 점이 자기 광선 위에
> 놓이므로 항등, 실측 0px). 그래서 획을 마치는 순간 화면에서 놀랄 일이 없고, 차이는
> **돌린 뒤에야** 보인다. D-S6이 지정한 중단 임계 대상이 바로 이 항등이었으므로 발동할 수
> 없었다 — 임계값은 두고 대상을 접합 이동량과 미배치율로 옮겼다(D-S7).
> **성립 조건은 도구가 아니라 입력에 걸린다**: 끝점 겨냥 오차가 그림 대각의 1% 근처여야 한다.

```
Stroke {
  id
  pts2d[]      // 원본 화면 좌표 (재투영·재계산용 보존)
  pts3d[]      // 3D 점열 (손떨림 포함)
  axis         // VP1|VP2|VP3|screen|face|free
  anchorRef    // 어디에 연결되었는가
  mesh         // TubeGeometry
  layer, color, width
}

Camera {
  vps[]        // 0~3개
  principal, f
  locked
}

Face {          // 선택적. 6절 참조
  strokes[]
  plane
}
```

**pts2d를 반드시 보존한다.** 카메라가 재조정되면 전체를 다시 투영해야 한다.

## 6. 면 — 미결 항목

"입체로 인식되는 순간" 면이 생기는가.

**A. 선만 유지**
순수 3D 스케치. 가림 처리 없음.
회전 후 앞뒤 구분이 안 되어 형태 판독이 어려울 수 있다.
참조 구현(sketchbook-v8)이 이 방식이며, 실제로 읽히는지 확인 가능하다.

**B. 닫힌 루프에서 면 생성**
가림 처리를 위해 필요. 회전 시 뒤쪽 선이 가려져야 형태가 읽힌다.
문제: 곡선 획이 만드는 루프는 완전한 평면이 아니다.
근사 평면 투영 또는 삼각분할이 필요하다.

**S-8에서 A로 먼저 만들고 판단한다.** 형태가 읽히면 B는 불필요하다.
면은 표시용이며, 사용자가 그린 것은 여전히 선이다.

## 7. 작업 순서

각 단계는 **브라우저에서 열리는 상태로** 커밋한다.
S-10까지 가야 실행 가능한 것이 나오는 구조를 만들지 않는다.

### S-0. 기반 정리
이전 계획의 폐기 항목 제거. 유지 항목 확인.
three.js(**0.185** — r128은 참조 구현의 버전이다, DECISIONS D-S1) + Vite, PWA 골격, 잉크 캡처.

### S-1. 카메라 확정 UI
§3 전체. 점 찍기 / 선 긋기 / 지평선 / 슬라이더 / 프리셋 / 그리드 / 유효성 검사.
**이 단계 끝에서 소실점을 찍고 그리드가 도는 것을 볼 수 있어야 한다.**

### S-2. 방향 판정
§4.1. VP 분류, 화면평행, 미분류.
크게 휜 획과 여러 축 획의 처리 방침을 여기서 결정한다.

### S-3. 획 → 3D
§4.2, §4.4, §4.5. 앵커 체인, 떨림 평면(두 방식 비교), 재투영.
**이 단계 끝에서 그린 획이 3D에 놓이고 회전해서 볼 수 있어야 한다.**

### S-4. 렌더링
튜브 메쉬(three.js TubeGeometry), 속도 기반 굵기, 캡.
온디맨드 렌더링(dirty flag).

### S-5. 회전 후 이어 그리기
돌린 뒤에는 카메라를 정확히 알므로 판정이 자명해진다.
소실점 설정 없이 바로 그려진다.
**이 단계가 이 도구의 핵심 기능이다.**

### S-6. 축 밖 획
§4.3. 면 위 사선, 경사 소실점, 자유 곡선 폴백.

### S-7. 편집
undo/redo, 지우개, 레이어, 선택·이동.

### S-8. 면 판단
§6. A로 먼저 확인하고 필요하면 B.

### S-9. 저장·배포
로컬 저장(IndexedDB), 내보내기(자체 JSON + OBJ 선 + glTF), PWA 완성.

### S-10. 종단 검증
Playwright. 카메라 확정 → 그리기 → 회전 → 이어 그리기 → 저장.
지연 측정, 스크린샷 회귀.

## 9. 위험

**획 → 3D 재투영의 자연스러움.** 미리보기와 확정 결과가 크게 다르면
사용자가 놀란다. S-3에서 측정하고, 차이가 크면 미리보기 방식을 바꾼다.

**축 판정 실패율.** 사용자가 숙련자라는 전제에 의존한다.
실패하면 미분류로 두고 사용자가 지정하게 한다 — 조용히 틀린 축에
배정하는 것보다 낫다.

**떨림 평면 선택.** §4.4. 회전 후 형태가 어색하면 이 선택이 원인이다.

**면 없이 형태가 읽히는가.** §6. 참조 구현이 선만으로 동작하므로
가능성이 높으나 확인 필요.
